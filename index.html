What this toolkit does

KeySense runs locally in your browser. Home contains seed and path controls, example printing and the Physical entropy lab. Key paths shows the derivation steps and tree inspector. Advanced practice offers limited word and path searches. All supported chains work offline when the complete set of files is kept together. Use disposable examples only. The app does not send wallet inputs to a server.

Stack: ethers v5 (BIP32 + UTXO crypto); tweetnacl + inline SLIP-0010 (Solana, Sui, Aptos); qrcode; @noble/hashes (BLAKE2b for Sui, SHA3-256 for Aptos). UTXO chains use zero extra libraries - pure inline Bech32 + ethers primitives. Theme stored in localStorage. All libraries live in src/vendor/ and are served from this site. The hosted release separately loads InsightFlare analytics; downloaded copies do not. To run it air-gapped, clone the repository and open the page with any local server.

What this toolkit does not do

It computes. It does not sign a transaction, does not broadcast anything to any network, and does not hold funds at any point, so there is nothing here to check a balance against or to "log into". A seed phrase and the addresses it derives are pure mathematics; using them to actually receive, send, or check funds needs a wallet application or a block explorer, not this page. Generate, back up, and understand a seed here if that helps, then use it in the software you intend to actually run it with.

Key observations
  • All EVM chains share coin_type = 60 - the same key yields the same 0x… address on Ethereum, Polygon, BSC, etc. (you still pay gas on the chain you use).
  • Bitcoin changes the purpose number (44 / 49 / 84 / 86) to pick address type, not just coin type.
  • Solana uses Ed25519 derivation (SLIP-0010). You cannot get a Solana address by plugging the same path into a raw secp256k1-only helper.
  • Ed25519 chains (Solana, Sui, Aptos) share the SLIP-0010 derivation pipeline. Every path segment must be hardened; there are no normal (unhardened) children. Sui hashes the public key with BLAKE2b-256 after a 0x00 scheme byte; Aptos hashes it with SHA3-256 followed by a 0x00 scheme byte for the legacy (default) account type, and has a separate SingleKey address scheme from the same key. Neither address is the public key itself, even though a Sui address is the same 32-byte length.
  • Cosmos uses the same secp256k1 curve as Bitcoin/Ethereum, but its address is Bech32 with the cosmos HRP over a raw 20-byte hash160 - not a Bitcoin-style witness version.
  • Non-standard paths are valid mathematically but wallets may not scan them - backup risk.
  • Why every EVM chain shares coin type 60: the address is derived from the key alone, and nothing in it names a chain. Ethereum, Polygon, BSC, Arbitrum, Optimism and Avalanche C-Chain all read the same 0x… as yours. The chain is chosen by the network you broadcast to, not by the address, which is why funds sent on the wrong network still land at "your" address but need that network's gas to move.
  • Why Bitcoin changes purpose rather than coin type: it is one currency with several address encodings. 44, 49, 84 and 86 all derive from the same seed on coin type 0, but produce 1…, 3…, bc1q… and bc1p…. Restoring a seed in a wallet that only scans one purpose is the usual reason coins look missing: they are at a different purpose on the same seed.
  • Why Ed25519 chains have no watch-only xpub: an xpub works because a parent public key can derive child public keys without the private key. SLIP-0010 on Ed25519 defines only hardened derivation, and hardened steps feed the private key into the hash, so there is nothing a public key alone can extend. That is a property of the curve's use here, not a missing feature.
  • What an xpub actually leaks: on its own it exposes every address in that branch, so all your balances and history, but not the ability to spend. Combine it with any one unhardened child private key, though, and the parent private key can be reconstructed, which hands over the whole branch. That is exactly why the standard paths harden purpose, coin type and account.

Learning Path: From Seed to Address

Walk through the key stages of HD wallet derivation. Each step builds on the previous one.

1. The Seed Phrase

Predict first: twelve ordinary words keep your money safe. Where does that safety come from?

A seed phrase can rebuild a tree of keys. Keep it secret. Some wallets also need a passphrase, shared signing rules or other recovery data. Nobody can reset a lost private key for you.

Before you read on: which of these are true?

Answer each one in your head first, then open it. Being wrong here is normal.

I can choose my own seed phrase, the way I choose a password.

No. A computer generates it from randomness. If you pick the words yourself, you hand the guessing to whoever guesses like you. In one survey of 643 wallet users, 58 percent believed they could choose their phrase the way they choose a password.

If I lose my seed phrase, someone can reset it for me.

No. There is no account and no reset, for anyone. The words are the wallet, not a login for it.

My coins are in the app, or on the device I use.

No. Coins sit on the blockchain. The app and the device only read the words you hold. Among people who already run their own wallet, three quarters of what they described never mentioned protecting the phrase.

Those figures come from one study of 643 wallet users plus 20 interviews (CHI 2025). The same study found that only 43 percent of people could pick a seed phrase out of a set of images.

What the words actually are

Your phrase is a written form of one long random number. That number is called entropy. Everything else in this walkthrough is arithmetic on it.

A word you will keep meeting: entropy

Entropy means randomness, counted in bits. One bit is one yes or no question. Every extra bit doubles the number of guesses an attacker needs. So 128 bits is not twice as strong as 64 bits. It is 264 times as strong.

  • 12 words carry 128 bits of entropy, plus 4 bits of checksum.
  • 24 words carry 256 bits of entropy, plus 8 bits of checksum.
  • The last word is partly decided by the checksum of the words before it.
  • The word list holds exactly 2048 words, so each word carries 11 bits.
Entropy (128-256 bits) | v BIP39 Checksum (4-8 bits) | v Split into 11-bit chunks - each maps to a word from the 2048-word list | v Mnemonic phrase (12 or 24 words) | v PBKDF2(mnemonic, passphrase, 2048 rounds) - 512-bit seed

By default this tool uses the browser CSPRNG. That is not a plain software random number generator. It is a thin wrapper over the operating system, which seeds itself from hardware noise such as thermal noise in the CPU and interrupt timing.

If you would rather not depend on that, open the Physical entropy lab on Home with Expert mode on. Type your own dice rolls or coin flips. The SHA-256 hash of what you type becomes the entropy.

The value of real dice is not that they are more random than the CPU. It is that they do not depend on your machine, so malware on it cannot predict them. The simulate buttons in that panel use the browser CSPRNG, so real throws are what count.

How much randomness is really in there?

Every option below makes a phrase that looks equally convincing. What differs is how many guesses stand between an attacker and your coins. Type a passphrase to see where your own idea would land.

Move this and watch every row change. Notice what stays true at any speed. 128 bits stays out of reach, while the weak rows fall to a patient attacker rather than a fast one.

Go deeper: why inventing your own phrase is worse, not just riskier.

Ten random words from a 7776 word list would reach about 2129, which is the same strength as twelve BIP39 words.

But if you can memorise ten random words, you can memorise a twelve word BIP39 phrase. That phrase carries a checksum, which catches typos, and every wallet can restore it. So inventing your own is not merely riskier. It is worse at the one job it was supposed to do.

Same 12 words, different passphrase

The BIP39 passphrase is a second, separate secret. It does not change the randomness of those words. The same words with no passphrase and with a passphrase are two unrelated wallets.

A wrong passphrase can make a restored wallet look empty. Each passphrase opens a different wallet. There is no wrong-passphrase warning.

Why a valid phrase can still be weak

Imagine a broken random source that can produce only a small set of starting values. Each value can still become a phrase with a valid checksum. The words look normal, but an attacker has far fewer guesses to try.

A checksum checks the encoding. It does not measure how the source chose its bits. This is why a phrase can pass a word check and still be easy to guess.

KeySense checks for obvious random-source failures when it loads. These checks cannot prove that a source is secure. Real dice can add an outside source, but typing the rolls into a compromised device still exposes them.

Which defence stops which failure

After an incident like that one, the useful question is not what is safest. It is which defence protects against which failure, and at which moment. These are the ones that matter, with their limits:

  • Your own dice protect at creation time only. Real rolls add a source outside the browser. Malware can still read them when typed. They cannot fix seeds made earlier.
  • A passphrase selects a different wallet. It does not repair a weak one. A strong, secret passphrase adds a barrier. A guessed or exposed passphrase does not. Do not rely on it to rescue weak words.
  • An update cannot fix a seed you already made. It stays weak forever. The remedy is a fresh seed, then moving the funds. Questions about whether a device was affected are urgent after any random number disclosure.
  • Verification catches bugs before they cost you. Deriving one seed in two independent tools and comparing addresses is the cheapest end-to-end check there is. This page verifies itself against the official BIP vectors live.
  • Failing closed beats failing quietly. A tool with no working randomness should refuse to generate anything, and this one does. A convincing phrase from a broken source is worse than an honest error.

Check your understanding

Answer in your head first, then open the question. Recalling an answer before seeing it is what makes it stick.

Where is your wallet, really?

In the words. The app and the device only read them, and so does any other wallet you later restore them into. Why this matters: anything that asks for the words is asking for the wallet.

How many bits of real entropy are in a 12-word phrase?

128. Twelve words carry 132 bits, and the last 4 are the checksum, so the secret part is 128 bits. A 24-word phrase carries 256.

You restore your wallet and mistype one word. What happens?

Almost always the wallet refuses, because the checksum no longer matches. There is a 1 in 16 chance with 12 words, or 1 in 256 with 24 words, that the mistake still passes and derives a different, empty wallet. That is why typing carefully matters.

Could you reset or recover your phrase if you lost it?

No. Nobody holds a copy, including this tool. Your real options are backing the words up properly, or moving funds to a new wallet with a new phrase.

Does adding a strong passphrase make a weakly generated seed safe?

No. The passphrase selects a different branch of a tree whose root is still guessable. Why this matters: an attacker who sweeps the seed can sweep the passphrase branches too.

Why is it never safe to type your seed into a website that offers to check it?

Because the words are the wallet itself, not a login name. Why this matters: whoever receives them can derive every key and spend everything within minutes.

2. From Seed to Master Key (BIP32)

Predict first: the tool cuts one long number into two halves. What could each half be for?

Your words become one long random number: the seed. One scramble step then cuts it into two halves.

  • HMAC-SHA512 is that scramble step. It mixes a key and a message into a result of fixed length that cannot be turned back. Here the key is the text "Bitcoin seed", and the message is your seed.
  • Left 256 bits become the master private key. This is the root secret.
  • Right 256 bits become the master chain code. This is extra randomness for child keys.
  • Every child key in the tree comes from this one master node.
With your seed
Go deeper: the exact recipe and its names
512-bit seed (from PBKDF2) | v HMAC-SHA512(key="Bitcoin seed", data=seed) | +--- Left 256 bits: Master Private Key | +--- Right 256 bits: Master Chain Code | v Master Node (m) = private key + chain code | v Child keys: CKD(parent, index) - child private key + child chain code

The seed comes from PBKDF2, run over your words. A passphrase is mixed in at that step. So the same words with a different passphrase give an unrelated tree, not a hardened version of it.

Check your understanding

What two values does HMAC-SHA512 produce at the root of the tree?

The left 256 bits become the master private key. The right 256 bits become the master chain code. Child derivation needs both.

Does the BIP39 passphrase change the master key?

Yes. It is mixed in before HMAC-SHA512 runs. A different passphrase gives a completely unrelated tree with the same words.

Why does child derivation need the chain code as well as the parent private key?

The chain code carries the extra randomness that makes each child unique and repeatable. Why this matters: one private key alone cannot rebuild the tree, so a backup has to be the words, not one key.

3. The Derivation Path

Predict first: a path reads like m/44'/0'/0'/0/0. What do you think each step does?

A derivation path navigates the HD key tree. Each level has a specific purpose.

Check your understanding

In m/84'/0'/0'/0/0, what does the 84 tell you?

The purpose: native segwit (bech32, bc1q...). 44 is legacy, 49 is wrapped segwit, 86 is taproot.

Your words are correct but the restored wallet shows zero balance. What are the first two suspects?

A different derivation path (purpose, account, or a wallet's non-standard default) or a passphrase you forgot setting. Try the Path recovery tool on the Advanced practice tab.

What changes in the path when you switch from account 0 to account 1, and what stays the same?

Only the account segment moves from 0' to 1'; purpose, coin type, change and index stay put. Why this matters: one segment of difference selects a fully separate wallet branch with its own addresses.

4. Hardened vs Normal Derivation

Predict first: one small mark, an apostrophe, changes how a key can be derived. What might it be protecting?

The apostrophe (') means hardened - the child key requires the parent private key, not just the public key.

TypeSecurity / UXTypical use
Hardened (')Higher isolation; cannot derive from watch-only parent xpubpurpose, coin_type, account; Solana last segment
NormalDerivable from xpub; useful for generating receiving addresses without the private keychange + index on Bitcoin-like chains

Why harden the first levels? If someone gets your xpub for account 0, they can derive all addresses in that account. But they cannot derive hardened children, so the master key and sibling accounts remain safe.

Ed25519 chains are fully hardened. Solana, Sui, and Aptos use Ed25519 keys via SLIP-0010. SLIP-0010 requires every path segment to be hardened, not just the first few. This is why their paths look like m/44'/501'/0'/0' with no unhardened levels.

Check your understanding

Your account xpub leaks. What exactly is exposed?

Every address that account can derive (present and future) and therefore your balances and transaction history. Not exposed: private keys, the master key, and sibling hardened accounts.

Why is every level hardened on Solana, Sui and Aptos?

They use Ed25519 via SLIP-0010, and SLIP-0010 requires hardened derivation at every level. Normal (non-hardened) derivation does not exist on those chains.

Why does an xpub plus one normal child private key expose the whole account?

Because normal child math can be run backwards from the child key to the parent key using only public data. Why this matters: a watch-only xpub stops being watch-only the moment one child private key leaks beside it.

5. From Private Key to Address

Predict first: the last step throws information away on purpose. Why is that safe?

The private key produces a public key. The public key is then hashed and encoded into an address. This segment follows that route for the two chains most people meet first.

Before you read on
Is an address just your public key, written out?

No. It is a hash of the public key, shortened and then encoded. You cannot get the key back out of the address.

Does your private key leave this page to work out an address?

No. The arithmetic runs in this browser tab, using libraries served from this same site.

Check your understanding

Can you work backwards, from an address to the public key?

No. Hashing runs one way on purpose. That is what makes an address safe to publish while the key behind it stays private.

Both routes above start with a secp256k1 public key. Where do they part company?

At the hash. Ethereum takes Keccak-256 and keeps the last 20 bytes. Bitcoin takes SHA-256 and then RIPEMD-160, then adds a version byte and a checksum before encoding.

6. One Key, Many Addresses

Predict first: the same key can be written as an address starting with 1, with 3, with bc1q or with bc1p. What changes?

The same words give a different looking address on every chain. Here is why that happens, and how to check that you are looking at the right one.

Solana

Private key (Ed25519) - public key (32 bytes) - Base58 encode - address

Tron

Same as Ethereum (Keccak-256 of public key) but encoded as Base58Check starting with T

Cosmos

Same secp256k1 curve as Bitcoin/Ethereum, but the address is Bech32 with the cosmos HRP over the raw 20-byte hash160 of the compressed public key (no witness version byte).

Sui

Ed25519 key (SLIP-0010). The address is 0x + BLAKE2b-256(0x00 scheme flag || 32-byte public key). It is not the public key itself, even though both are 32 bytes.

Aptos

Ed25519 key (SLIP-0010). This tool shows the legacy address: 0x + SHA3-256(32-byte public key || 0x00 scheme byte), which is the SDK and wallet default. Aptos also has SingleKey (unified) accounts from the same seed with a different address. SHA3-256 is not Keccak-256. Hashing uses a vendored SHA3-256 (Web Crypto has no SHA3).

One seed, nine chains

The same words, the same account 0, index 0, derived into every chain this tool supports, side by side. Nine different-looking addresses, nine different key derivations, one seed underneath all of them.

Check your understanding

Same seed, Ethereum and Tron: same private key?

No. Coin type 60 and 195 are different hardened branches, so different keys. Tron's address then formats the Ethereum-style hash as Base58Check starting with T.

Is a Sui address just the public key in hex?

No. It is BLAKE2b-256 of a scheme flag byte plus the public key. Both are 32 bytes, which is exactly why people assume they are the same thing.

Why does the same seed show a 0x address on Ethereum and a bc1q address on Bitcoin?

Because the paths differ (coin type 60 vs 0, purpose 44 vs 84) so the keys differ, and each chain then encodes its key differently. Why this matters: one seed holds many independent wallets, so checking one chain never tells you about the others.

Practice everything at once

Each segment above ends with a few questions. These mix all six together, the way a real problem arrives, with no label telling you which part of the tree you are looking at. Answer first, then open the answer.

Your 12 words give a bc1q address in one wallet and an address starting with 1 in another. Is one of them wrong?

No. Both are real addresses on the same seed. They sit on different branches, because the two wallets default to a different purpose (84 against 44). A wallet only shows you the branch it knows about.

You write your 12 words down in the wrong order. Does the wallet still open?

Almost never. The order is part of the value, and a wrong order usually fails the checksum. About 1 time in 16 for 12 words it passes anyway and builds a different, empty wallet, which is the dangerous case.

Someone photographs your account xpub. What can they see, and what can they not see?

They can see every address that account will ever use, so your balance and your history. They cannot see your private keys, your master key, or the other accounts on your seed.

Which half of the master node is the root secret, and which half keeps child keys different?

The master private key is the root secret. The master chain code is the extra randomness that makes each child unique. Child derivation needs both.

Your words are right but a restored wallet shows zero. What are the first two suspects?

A different derivation path (purpose, account, or a wallet's own unusual default), or a passphrase you have forgotten you set. Both change the branch, so the wallet looks empty rather than wrong.

Why does the same seed give a different private key on Ethereum and on Bitcoin?

Coin type is part of the path and it is hardened, so 60 and 0 land on two different branches. Different branches, different keys.

A stranger says word order does not matter, because the set of words is the same. Right or wrong?

Wrong. Order changes the entropy, so it changes every key below it. The same set of words in a different order is a different wallet, or no wallet at all.

Why can an address be published while the private key cannot?

Because the steps from key to address run one way. A hash cannot be undone, so publishing an address gives nothing that leads back to the key.

Your friend shares an xpub and one child private key from an unhardened level. What have they given away?

The whole account. The unhardened step can be run backwards from the child key plus the public data, which rebuilds the parent private key. A watch-only wallet stops being watch-only at that moment.

A 24 word phrase against a 12 word phrase: how much more guessing does it cost an attacker?

128 more bits of guessing, which takes it from about 2^128 to about 2^256. Both are far out of reach today, so the weak point is rarely the length. It is how the words were made.

Explain it in your own words

Check these two ideas. Say your answer out loud first. Then open the model answer. There is more to learn beyond this page.

Explain why a backup needs more than a list of words in some wallets.

A model answer: seed words can rebuild keys, but the wallet may also use a passphrase. Some wallets need rules and more than one signer. Paths help find the right keys. The network matters too. List what your wallet needs. Do not put secrets in that list. A paper copy avoids some online risks but can still be lost, copied or damaged. Try a restore with a public test seed first.

Explain why a wallet can show an empty balance even when your words are correct.

A model answer: the words do not lead to one wallet. They lead to a tree, and a wallet only looks at the branches it knows about. Two wallets can default to a different branch from the same words, so each one shows a different set of addresses. The funds are not lost. They are on a branch you are not looking at. So the first thing to check is the path, and then whether a passphrase was mixed in.

What is the real offer?

Every scam around seed phrases is a version of one trick: getting you to expose the words. Read each scenario, decide what is really being asked, then open it to compare.

A stranger in a forum offers to "verify your recovery phrase is safe" using their professional tool.

The offer is: give me your words. There is nothing to verify - a valid phrase is valid. Whoever receives it owns the wallet within minutes.

"Wallet support" asks you to read your 12 words aloud to "restore your account after suspicious activity".

No legitimate support channel, ever, asks for the words. The words are not a credential you present; they are the wallet itself. The "suspicious activity" is this conversation.

A site asks you to type your seed phrase to "check whether your wallet is affected by the latest RNG bug".

A phrase already generated cannot be checked for bugs by looking at it - the risk lived in the device that made it, at creation time. Typing it anywhere simply hands it over.

An airdrop form says "connect your wallet by entering your seed phrase".

Connecting a wallet never involves the phrase - signatures and approvals expose nothing reusable. Any input field asking for it is a drain attempt, however professional the page looks.

Plain-language glossary

The jargon of this page in one place.

Entropy
The actual random data behind a seed. Everything else - words, keys, addresses - is derived from it. Its length in bits is the real strength of a wallet.
Checksum
A few extra bits computed from the entropy and appended before encoding, so that typos produce an invalid phrase instead of a different valid-looking wallet.
Mnemonic
The 12-24 word phrase: a human-writable encoding of entropy plus checksum, one word per 11 bits.
Seed (BIP39)
Not the words themselves. The 512-bit value PBKDF2 produces from mnemonic plus passphrase; the root of all keys.
Master key / chain code
The two halves of HMAC-SHA512 at the root: the first private key, and the entropy used to derive children deterministically.
xprv / xpub
Serialized extended keys: a key plus its chain code. An xpub alone can derive child addresses but no private keys.
Hardened (')
A derivation step that needs the parent private key. It cannot be computed from an xpub, which is why account levels are hardened.
Derivation path
The route through the key tree, like m/44'/60'/0'/0/0. Same seed plus different path equals different keys.
Purpose / coin type
First two path levels: which BIP standard (44, 49, 84, 86) and which chain (SLIP-0044 registry: 0 BTC, 60 ETH, 501 SOL...).
WIF
Wallet Import Format: a private key packaged for copy-paste between Bitcoin wallets.
Bech32 / HRP
The address alphabet Bitcoin segwit uses, and its human-readable prefix (bc, cosmos, ltc...).
secp256k1 / Ed25519
The two signing curves here. Bitcoin, Ethereum and friends use secp256k1; Solana, Sui and Aptos use Ed25519, whose derivation (SLIP-0010) is hardened at every level.
Frequently asked
Why exactly 2048 words?

2048 is 211, so each word encodes exactly 11 bits with no waste. 12 words x 11 bits = 132 bits = 128 entropy + 4 checksum.

Are 12 words enough, or do I need 24?

128 bits of entropy is already beyond any brute-force horizon; 24 words (256 bits) mainly help when you trust the phrase to survive partial exposure or want headroom against future attacks.

Can two different seeds ever produce the same address?

Mathematically possible, practically impossible: the space of seeds is so much larger than the space of addresses that a collision has never occurred by chance.

Why does my restored wallet show an empty balance?

Usually a different derivation path (try the Path recovery tool on the Advanced practice tab) or a passphrase set long ago and forgotten. The funds are almost certainly fine.

What does the last word do that is special?

It carries the checksum: in a 12-word phrase its last 4 bits are computed from all 128 entropy bits, so it is not freely choosable.

Is the passphrase stored or recoverable anywhere?

No. It only selects which branch of the tree exists. Forget it and that wallet is unreachable with today's technology, by design.
